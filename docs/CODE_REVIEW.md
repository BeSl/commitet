# Обзор кодовой базы: поддерживаемость и стабильность

Документ фиксирует результаты сквозного аудита проекта и дорожную карту по
улучшению поддерживаемости и стабильности. Отметки статуса:

- ✅ — сделано в рамках текущей итерации
- 🔲 — запланировано (требует отдельной работы/обсуждения)

---

## 1. Конкурентность и потокобезопасность

| Статус | Проблема | Решение |
|--------|----------|---------|
| ✅ | **`ShellExecutor` — синглтон с изменяемым состоянием** (`workingDir`, `timeout`). `GitCommandHelper` перезаписывал эти поля при каждом вызове; параллельные вызовы (Quartz, RabbitMQ, UI) могли выполнить команду в чужом каталоге. | `ShellExecutor` сделан без состояния — каталог и таймаут передаются параметрами каждого вызова. |
| ✅ | **Параллельные запуски Quartz-задачи `Committer`** при интервале 5 c и долгом push приводили к двойной обработке одного коммита. | Добавлена аннотация `@DisallowConcurrentExecution`. |
| ✅ | **Ручное создание `ShellExecutor(...)`** в `FileServiceImpl`, `OneRunner`, `CommitetJmApplication` (дублирование, обход DI). | Везде используется единый бин-синглтон. |
| 🔲 | **Нет защиты от выборки одного коммита двумя обработчиками** (`findNextCommitToProcess`). Сейчас защищено `@DisallowConcurrentExecution`, но при горизонтальном масштабировании (несколько инстансов) этого недостаточно. | Пессимистичная блокировка строки (`LockModeType.PESSIMISTIC_WRITE`) или атомарный апдейт статуса `NEW → PROCESSED` с условием. |

## 2. Утечки ресурсов и работа с процессами

| Статус | Проблема | Решение |
|--------|----------|---------|
| 🔲 | **Возможный дедлок/обрезка вывода в `ShellExecutor`**: вывод читается ПОСЛЕ `waitFor`. На большом выводе пайп-буфер переполняется и процесс блокируется до таймаута. | Читать stdout/stderr в отдельных потоках (или `redirectErrorStream` + потоковое чтение) до `waitFor`. |
| 🔲 | **Игнорируется результат `renameTo`/`delete`** — частично закрыто (`OneCFileUtils` теперь логирует неудачи ✅), но в других местах стоит проверять. | Проверять возвращаемое значение или использовать `Files.move`/`Files.delete` с исключениями. |
| ✅ | `OneCFileUtils.filterAndRenameFiles` — неудачные `delete`/`renameTo` теперь логируются. | — |

## 3. Запросы к БД (риск OOM)

| Статус | Проблема | Решение |
|--------|----------|---------|
| 🔲 | **Неограниченные выборки** `.list()` без пагинации: `ConfigMetadataService.loadExistingItems`, `ChatHistoryService.getUserChats`, `AvailableNameService.getAllAvailableNames`. На больших конфигурациях 1С (десятки тысяч объектов) — риск OOM. | Постраничная обработка (`firstResult`/`maxResults`) либо проекции/стримы. Для импорта метаданных — батчи по 1000. |

## 4. Обработка ошибок и транзакции

| Статус | Проблема | Решение |
|--------|----------|---------|
| 🔲 | **`createCommit()` не атомарен**: статус выставляется в `PROCESSED`, при дальнейшей ошибке коммит «зависает». | НЕ оборачивать весь метод в `@Transactional` (внутри долгие shell-операции git — нельзя держать транзакцию/соединение). Вместо этого: гарантированно переводить статус в `ERROR` в `catch` (уже частично есть) и добавить «таймаут зависших PROCESSED» (повторный захват по времени). |
| 🔲 | **Проглоченное исключение** в `findNextCommitToProcess` (возвращает `null` при сбое БД — задача молча простаивает). | Логировать как ошибку и пробрасывать, чтобы сбой был заметен в мониторинге. |
| 🔲 | **Разнородная сигнализация ошибок**: `Pair<Boolean,String>` (`GitService`), DTO `CommitCreateResponse`, `RuntimeException` (`OneRunner`). | Единый подход: либо sealed `Result<T>`, либо иерархия доменных исключений + общий `@RestControllerAdvice`. |
| 🔲 | **Широкие `catch (Exception)`** в контроллере без различения 4xx/5xx. | Разделить по типам (`IllegalArgumentException`→400, доменные→422, прочее→500) через `@ExceptionHandler`. |
| ✅ | **Валидация в контроллере, в обход сервиса** (путь RabbitMQ не валидировался). | Валидация перенесена в `CommitRestService.validate()`, используется и REST, и очередью. |

## 5. Сообщения RabbitMQ

| Статус | Проблема | Решение |
|--------|----------|---------|
| 🔲 | **Нет DLQ и явной стратегии повторов**. Сейчас «ядовитые» сообщения отбрасываются (`defaultRequeueRejected=false`), бизнес-ошибки логируются. Потеря транзиентно-сбойных сообщений возможна. | Настроить dead-letter-exchange + ограниченные ретраи (`RetryInterceptor`) для отделения транзиентных сбоев от перманентных. |
